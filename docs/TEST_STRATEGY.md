## 1. Spec characteristics that shape this strategy

- **574 operations / 549 paths.** Methods: GET 245, POST 192, PUT 75, DELETE 53, PATCH 9.
- **Single auth scheme:** `bearerAuth` (HTTP bearer/JWT), declared globally, never overridden per-operation.
  Only one `servers` entry (`http://localhost:3000`) — dev/staging/prod base URLs are **not** in the spec and must come from our own env config.
- **Auth is under-modeled:** 388/574 ops (68%) carry an `Authorization` header param + a "🔒 Requires Authentication" note in `description`; the other 186 have neither. This is a text convention, not a formal `security: []` override — treat it as a *hint*, not ground truth, and confirm the real 401 behavior empirically per endpoint during implementation.
- **No usable request/response schemas.** `components.schemas` is empty, zero `$ref` usage anywhere. Every response is declared `text/plain` with a bare string, including 200/201 JSON bodies. Only 200/201 status codes are documented — no 4xx/5xx contracts at all. This is a straight Postman-collection → OpenAPI conversion, not a hand-authored contract.
  **Consequence:** we cannot generate Ajv/Zod validators from the spec. Response contracts must be reverse-engineered from real calls as each domain is implemented, then checked into `src/utils/validators/<domain>.schema.ts` and treated as living documentation of *actual* behavior.
- **112 raw tags, one-endpoint-per-request-name style, with duplicates/typos:** `Boomarks`/`Bookmarks`/`Bookmark`, `Insitution`/`Institution`, `Clarfication`/`Clarification`/`Clarifications`, `Booktype`/`Booktypes`, `Countries`/`Country`, singular/plural pairs throughout, plus ~40 singleton verb-named tags (`GetAllEmployee`, `DeleteAddress`, `SaveOfficeType`...). Raw tags are not a usable test-suite grouping as-is.

## 3. Phased rollout (maps to CLAUDE.md Step 5: Auth → Core Entities → Edge Cases)

1. **Auth/User/Session** (`user` domain, ~25 ops) — must land first; every other domain's fixtures depend on a working bearer-token flow.
2. **Core entities by volume:** `content`, `diary`, `management`, `institution`, `admin`, `planning`, `book-catalog`, `hr-staff`, `draft` — in that order (≈75% of all operations).
3. **Secondary entities:** `variables`, `bookmarks`, `kampus`, `menu`, `geo-master-data`, `student`, `assessment`, `clarification`, `notes`, `offline`, `company`.
4. **Long tail / `misc`:** scoped per-endpoint once the pattern library (fixtures, factories, validators) is proven on the domains above — highest risk of being genuinely dead/unused endpoints, worth a quick manual triage before writing tests.
5. **Edge cases** are woven into each domain's test file as it's built (boundary values, auth-negative, 404/409/422 paths), not a separate late pass — waiting until the end to add edge cases means re-opening every domain file twice.

## 4. Coverage strategy per endpoint

Since the spec gives no real contract, each test asserts, in order:
1. HTTP status code (happy path + at least one negative path: missing/invalid auth, invalid payload, not-found id).
2. Required headers (`Content-Type`, any custom headers observed in real responses).
3. **Discovered** response shape via a per-domain Zod schema written from the actual first successful call, not from the spec — this schema is the enforced contract from that point on, catching regressions even though the spec never had one.
4. Business-logic invariants (e.g., created resource is retrievable, delete is idempotent-or-404, list endpoints respect any pagination/filter params actually observed).

Auth handling: default fixture attaches a valid bearer token to every request; a small allow-list of confirmed-public endpoints (built empirically, not from the description-text hint) skips it. Every domain gets at least one explicit 401/403 test against a real protected endpoint to validate the auth boundary actually holds, since the spec's per-op signal isn't trustworthy.

## 5. Bugzilla defect governance (ported from `kpost-testbench_v2`)

Reusing the proven pattern rather than reinventing it:
- Fingerprint-based dedupe (SHA1 of normalized endpoint+validator+message, volatile substrings like UUIDs/JWTs/timestamps collapsed first) tagged into the bug summary/whiteboard — catches the same fault even if wording drifts.
- Fallback fault-key index (`product||endpoint||validator`) and a phrase-search adoption path for bugs filed before the bench existed.
- Bugzilla auth via `api_key` query param (not header) — this reference instance ignores the header form.
- `BugzillaReporter` as a custom Playwright `Reporter`, wired to run in `onEnd()`, skipped in CI in favor of filing off the merged blob report (avoids double-filing on sharded runs).
- Config split: `env.ts` (Zod-validated env), `bugzilla.config.ts` (severity/priority maps, dedupe tag prefix), `ownership.config.ts` (product/component/assignee per test-suite/domain).

**This part is blocked on real values** — see open questions below.

## 6. Risks / findings to carry forward

- Credentials appear in a URL path for `kampus` book-view (`/v1/kampus/book/view/{sessionId}/{username}/{password}/...`) — worth flagging as a security concern alongside functional testing, not just testing it as designed.
- `Institution` vs `Ias` tags both do institution CRUD — likely duplicate/legacy endpoints; needs confirmation before writing double coverage.
- No documented error schema anywhere — error-path assertions will necessarily be looser (status code + maybe a generic shape) until real error bodies are observed.
- Single `localhost:3000` server in the spec — environment base URLs are entirely our own config, not derived from the spec.
- **CONFIRMED (live test, `src/tests/user/login.spec.ts`): `GET /v1/user/profile` returns the requesting user's bcrypt password hash in `user.password`.** No endpoint should ever return credential material, hashed or not. A regression test asserting this (currently red on purpose) is in place; will auto-file to Bugzilla once that's configured (section 5).
- Per the backend's own architecture docs (`D:\KATBOOK\KatbookInitiation_API\docs\`): there are **two different JWT auth middlewares** — `needsAuth` (verifies signature via passport-jwt) and `authToken`/`CheckTokenExists` (does **not** verify signature). Worth a dedicated security test per domain once we start touching routes that use the second one — confirm this from the routes themselves as each domain is implemented, don't assume the docs' claim.
- Same docs: **338 of 750 routes have no auth at all** (route-scan count, backend has 750 routes vs. swagger.json's 574 — the swagger is incomplete, missing ~176 routes; the domain consolidation in section 2 is scoped to what's in swagger.json only).

## 9. `management` domain — findings (all 24 endpoints covered)

**Part 1 — plain CRUD** (`src/tests/management/management.spec.ts`, 22 tests): `Preparations`/`Uploadings` sub-resources under `/v1/management/preparations` and `/v1/management/uploadings`. Read directly from `ManagementPreparation.controller.js` / `ManagementUploading.controller.js` since swagger's schema is generic.

**Part 2 — bulk task-assignment workflow** (`src/tests/management/management-planning.spec.ts`, 34 tests): `/v1/management/preparations/planning` and `/v1/management/uploadings/planning` (+ `/user/planning`, `/:id` variants) — `ManagementPlanningPreparationController`/`ManagementUploadingPreparationController`. Bulk `{"data": [...]}` payloads, each item validated then checked against: caller's own usertype (admin can assign to anyone; non-admin can only self-assign), company existence, assignee existence (must be an active `User` in the *caller's own* `companyId`, not the item's `companyId`), and that `selectedActivities` references a real Part-1 resource. Status workflow is `Pending` (set automatically on create, not settable) → `InProgress`/`Completed` (only these two are valid update targets). A record's "already exists for this period" duplicate check is keyed on `(company, assignee, activity, esd, efd)` and excludes `Completed` records — tests sidestep this by creating a fresh Part-1 activity per test rather than varying dates.

**Findings** (asserted as current actual behavior, not treated as test failures — logged here for the backend team):
- Empty result sets are modeled as `404` ("No Management Preparations found" / "No Management planning preparation found!"), not `200` + `[]`, across both parts — every domain going forward should check this same-shape-or-not before assuming REST convention.
- Several Part-1 response messages are copy-pasted across resources: `CreateManagementUploading`'s success message says "Management Preparation saved successfully" (not Uploading); its admin-gate message says "...create ContentPreparation!." (a third, unrelated resource name); `GetManagementUploadingsById`'s not-found message says "Management Preparation not found." Part 2's messages are correctly resource-specific throughout (developer vs uploader wording is consistent), unlike Part 1.
- `UpdateManagementPreparation`/`UpdateManagementUploading` (Part 1) have **no admin/usertype gate**, unlike their sibling `Create`/`Delete` handlers on the same resource (which require `usertype.code === 'MA@1'`) — worth a dedicated RBAC test once a non-admin (Content Developer/Uploader) test actor exists, to confirm whether this is intentional or a gap.
- **SECURITY (2nd instance of the `/v1/user/profile` leak, confirmed live):** `CreateManagementPlanningPreparation`/`CreateManagementUploadingPreparation` and both their update handlers assign the full `req.user` Mongoose document (not `user._id`) to `createdBy`/`updatedBy`. The create/update response therefore embeds the caller's full user record — **including the bcrypt password hash** — under `data[].createdBy`/`updatedBy`. This is a broader pattern than a single leaky endpoint: anywhere `req.user` gets attached directly to a document field instead of its `_id`, the same leak will recur. Regression-tested (intentionally red) as `SECURITY: create response must not leak the password hash via createdBy` in both Developer/Uploader variants.
- Minor: `UpdateManagementUploadingPreparationById` (`managementuploadingpreparation.controller.js:293-294`) has two leftover `console.log` debug statements logging the full request body — not a functional bug, but worth flagging for removal.
- All 24 routes (both parts) use `needsAuth` (the signature-verified middleware) — this domain is not exposed to the `authToken`/no-signature-check risk noted in section 6.
- Testing gotcha worth remembering for future domains: the first attempt at these tests leaked ~30 stray records into the shared dev DB because (a) two tests created resources without cleanup (fixed with an `afterEach` sweep), and (b) the intentionally-red security test's cleanup call was written *after* the failing assertion, so it never ran (fixed by moving cleanup into `finally`). Any test expected to stay permanently red still needs its cleanup to run unconditionally.

**Done**: `ContentType` (`src/tests/content/content-type.spec.ts`, `ContentType.controller.js`), `ContentAttribute` (`content-attribute.spec.ts`, `contentAttribute.controller.js`), `Scratch` (`scratch.spec.ts`, `scratchfile.controller.js`) — 21 tests total.

**Findings**:
- **BUG (routing, high value):** `POST /v1/content/attribute` is permanently unreachable. `routes/v1.js:380` registers `router.post('/content/:sessionId', needsAuth, requireParams, ContentController.GetSessionContentAndPlanningBySessionID)` — a fully generic one-segment POST pattern — *before* `router.post('/content/attribute', ...)` at line 798. Express matches POST routes in registration order, so every call to `/v1/content/attribute` is captured by the generic handler (treating `"attribute"` as `sessionId`), which then 400s via its `requireParams` middleware. The real `ContentAttributeController.CreateContentAttribute` is dead code — **there is currently no way to create a content attribute via this API, for any company.** `GetContentAttribute` (GET, different route shape) is unaffected but has nothing to ever return. Worth checking every other `/content/<literal>` POST/GET route registered after line 380/369 (their `:sessionId`/`:contentId` single-segment generic siblings) for the same shadowing risk before trusting any of them.
- **BUG (inverted validation, `ContentType.controller.js:178-181`):** `UpdateContentType`'s mappingType check is inverted — `if (CONFIG.contentMap.includes(mappingType)) return ReE(...)` rejects when the value **is** valid (`'Unit'`/`'Session'`) and silently accepts (and persists) anything else. Regression-tested as `BUG: update rejects switching to a valid mappingType but accepts an arbitrary invalid one` — confirms a record can be corrupted with an arbitrary string via this endpoint while legitimate updates are blocked.
- **SECURITY (high severity):** every `Scratch` route (`routes/v1.js:1024-1028`) has **no auth middleware at all**, and `scratchfile.controller.js` never filters by company or user — `GetAllScratchFiles` returns every active record system-wide, and `Update`/`DeleteScratchFileByID` accept any well-formed id with no ownership check. Confirmed live (not just from source): an anonymous caller can read, tamper with, or delete any scratch file created by anyone. 3 dedicated `SECURITY:` tests document this.
- `ContentType` create/update/delete are admin-gated (`usertype.code === 'MA@1'`, same pattern as `management`); `getAll` only needs a valid session (any authenticated user). All 4 routes use `needsAuth`.
- `ContentAttribute`'s create route uses `needsAuth` (moot, given the shadowing bug above); `getAll` is genuinely public — confirmed against `routes/v1.js:799` directly, not inferred from swagger's `🔓`/`🔒` markers (which have proven unreliable elsewhere).
- Investigated and ruled out during this work: `company.controller.js`'s `deleteCompany` references `UserType` with no import of it anywhere in the file — looked like a certain `ReferenceError`/500 on every call, but a direct live test (`DELETE /v1/company/:companyId`) returned `200 {"message":"Company deleted!"}` cleanly. Recorded here specifically so nobody re-flags it without testing live first — reading source alone was misleading this one time.

**Not yet covered at this point** (see section 11 for what got done next): the core `ContentController` (text/PDF/RAG pipeline, ~90 ops including V2), `ContentLinkController`, `ContentPreparationController`/`ContentUploadingController` "name" resources, `VideoScriptController`, `HandBookController`, `KAudioController`, `Editor`, `Highlighter` v1+v2, `Hyperlink` v1+v2, `History`.

## 11. Curriculum-tree unblock + second batch of `content` sub-domains

Verified end-to-end by creating and deleting a real `Highlighter` document with the discovered IDs. The full chain is checked into `CURRICULUM` in `src/config/seed.constants.ts` with citations — reuse it rather than re-discovering or fabricating curriculum data for any future domain (`diary`, `planning` almost certainly need it too).

**Done in this batch** (`src/tests/content/`): `editor.spec.ts` (4 ops), `highlighter.spec.ts` (10 ops, v1+v2), `hyperlink.spec.ts` (10 ops, v1+v2), `content-history.spec.ts` (5 ops, 1 deliberately unexercised), `content-preparation.spec.ts` (10 ops — the `ContentPreparation`/`ContentUploading` "name" resources, mirrors of `management`'s pattern), `videoscript.spec.ts` (4 ops), `handbook.spec.ts` (6 of 8 ops — `UpdateTeacherHandbook`'s dedicated PUT route and `GetAllTeachersHandbookByVariables`/`GetHandbookByQuery` not yet covered).

**Findings:**
- **CRITICAL SECURITY — confirmed exploitable, not just read from source:** `middleware/tokenparser.js`'s `authToken` middleware (guards `GET /content/videos/script/:id` and `POST /content/videos/scripts/...`) calls `jwt.decode()`, never `jwt.verify()` — the signature is never checked, only `exp`. A completely fabricated, unsigned token (`src/utils/forge-jwt.ts`) with a made-up user ID is accepted exactly like a real one; proven live in `videoscript.spec.ts`'s two `SECURITY:` tests. The same file also exports `CheckTokenExists`, used on 6 `Meeting` routes (`routes/v1.js:664-669`, out of scope for `content`), which is worse still — it only checks that *some* non-empty `Authorization` header is present, never even attempting to decode it. Flag both for the backend team as the same root defect: the "public" vs "needsAuth" distinction used throughout this whole API is not the real security boundary — routes using either of these two middlewares are effectively unauthenticated regardless of what token is sent.
- **3rd and 4th confirmed instances of the password-hash leak** (see section 9's first instance): `VideoScriptController.CreateScriptForVideo` and `HandBookController.CreateTeachersHandbook` both assign `req.user` (not `user._id`) to `createdBy`/`updatedBy`, so their create responses embed the full user document including the bcrypt hash. Same root cause as the `management-planning` instance — this is a systemic pattern across the codebase, not isolated incidents. Regression-tested (intentionally red) in `handbook.spec.ts`.
- **BUG (performance/reliability, confirmed hangs — 2 endpoints):** `EditorLoadController.GetAllEditorLoadEvents` (as Admin, aggregating every other user's load events) and `KAudioController.GetKAudioById` (see below) both hang indefinitely with zero response under real conditions — confirmed via direct timed `curl` before writing the tests (not a Playwright/network flake). Both are regression-tested with a bounded per-request timeout (`RequestOptions.timeout`, added to `BaseApiClient`) so a single test documents the hang in ~8s instead of consuming the full default timeout on every run.
- **BUG, likely severe:** `KAudioController.GetKAudioById` (`POST /content/kaudio/get/:id`) has no success-response path at all once the record is found — the function just ends after an unrelated, misapplied field check, so the request hangs until client timeout. Confirmed live.
- **BUG (structural, `handbook.controller.js` and `videoscript.controller.js`):** both controllers' "does this tier/variable actually exist and match" validation treats `tierDetails`/`variableDetails` as arrays in the initial field-presence check (`tierDetails.filter(...)`) but as single objects everywhere after (`tierDetails.tierId`). In practice this means `new ObjectId(undefined)` (which the mongodb driver treats as "generate a random ObjectId" rather than throwing) silently defeats the existence check, so the record saves with whatever tier/variable references were submitted, validated or not.
- Route auth is inconsistent per-endpoint within the same controller, same as elsewhere in this API: `Editor`/`ContentPreparation`/`ContentUploading`/`VideoScript` create-delete use `needsAuth` properly; `Highlighter`/`Hyperlink`/`ContentHistory` (all routes) and `HandBook`'s `GetAll*`/`GetHandbookByQuery` are fully public by design (confirmed against `routes/v1.js`, not assumed).
- `ContentHistory`'s `PUT /history/existinghistory/upload` (bulk R2 migration, up to 1000 records, no auth) is confirmed as a finding from source only — deliberately never invoked, even to prove the auth gap, since doing so would perform a real bulk mutation against the shared dev database.
